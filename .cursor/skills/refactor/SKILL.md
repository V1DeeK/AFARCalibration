# /refactor — рефакторинг без изменения поведения

## Предусловие

Сначала прогони тесты: `ctest --test-dir build --output-on-failure`.

- Прогон красный → рефакторинг не начинаем. Сначала `/implement` или
  `debugger`: нельзя отличить «сломал рефакторингом» от «было сломано».
- Затрагиваемый код не покрыт тестами → запусти `test-writer` и получи
  покрытие. Рефакторинг без сетки безопасности — это переписывание вслепую.

## Шаги

```
- [ ] 1. Анализ — субагент senior-reviewer
- [ ] 2. Согласование целей с пользователем
- [ ] 3. Преобразование — субагент refactorer
- [ ] 4. Проверка — субагент test-runner
- [ ] 5. Отчёт — субагент documenter
```

**Шаг 1.** `senior-reviewer` разбирает указанный участок и называет конкретные
проблемы структуры с приоритетом.

**Шаг 2.** Покажи пользователю список целей и спроси, какие берём. Рефакторинг
«всего сразу» не делаем: чем крупнее диф, тем бесполезнее ревью.

**Шаг 3.** `refactorer` выполняет согласованные преобразования по одному,
пересобирая после каждого.

**Шаг 4.** `test-runner` прогоняет полный набор. Любое изменение ожиданий
теста — признак того, что поведение поехало. В этом случае откатываем шаг,
а не правим тест.

**Шаг 5.** `documenter` фиксирует, что изменилось в структуре, если это влияет
на README или на то, как работать с модулем.

## Итог

Отчёт: какие преобразования применены, подтверждение что тесты зелёные и
ожидания не менялись, и отдельным списком — что найдено попутно, но сознательно
не исправлено.
