# Сборка агентов Cursor для AFAR RX Calibration Studio

Перенесено из `V1DeeK/RMO` (`.cursor/`) и перенастроено под программу
калибровки. Та же сборка для Claude Code лежит в `.claude/`; содержимое
агентов, скиллов и правил у них общее — меняя одно, правь и второе.
Прежний `.cursor/` из первой версии студента заменён: он описывал АРМ, а не
эту программу. Отдельная папка `commands/` и правило `orchestration.mdc`
больше не нужны — `/orchestrate` и остальные процессы вызываются из
`skills/`.

Четыре механизма Cursor, разложенные по назначению. Ниже — что это, как
пользоваться и как перенести в учётную запись.

```
.cursor/
├── agents/       11 субагентов — кто выполняет работу
├── skills/       12 скиллов — 5 процессов + 7 модулей знаний
├── rules/        7 правил — что действует без вызова
├── hooks/        скрипты хука (Windows/macOS/Linux) + общие правила
├── tools/        перенос конфигурации в учётную запись
├── config.json   конвенции проекта (наш файл, не настройка Cursor)
├── hooks.json    подтверждение перед необратимыми командами
└── workspace/    состояние текущей оркестрации, не коммитится
```

На схемах вроде [Cursor AI Setup](https://alexeytriplea.dev/ru/hub/cursor-setup)
процессы лежат в `commands/`. В текущем Cursor это то же самое, что скиллы
с `disable-model-invocation: true`: вызов `/implement`, `/orchestrate` и
остальных идёт из `skills/`. Отдельную папку `commands/` не заводим — иначе
в чате появятся два одинаковых пункта. Встроенная команда Cursor `/review`
открывает выбор Bugbot / Security Review, поэтому проверка перед коммитом
здесь называется `/review-changes`.

## Чем эти механизмы отличаются

| | Правило | Скилл | Субагент |
|---|---|---|---|
| Когда попадает в работу | само, по условию из frontmatter | по `/имя` или когда подойдёт описание | когда основной агент делегирует, или по `/имя` |
| Контекст | добавляется к текущему чату | добавляется к текущему чату | **свой отдельный контекст** |
| Видит переписку | да | да | **нет** |
| Для чего | короткие ограничения | многошаговая процедура | роль с отдельным окном контекста |

Главное следствие: субагент не видит ни этот чат, ни что решили раньше.
Всё нужное передаётся в задании. Поэтому рабочие процессы (`skills/`)
описывают, **что именно** передать каждому субагенту.

## Субагенты

Вызов: `/имя` в чате, либо «запусти субагента worker и сделай …».
Основной агент вызывает их и сам, если описание подходит под задачу.

| Субагент | Роль | Правит код | Чем ограничен |
|---|---|---|---|
| `planner` | делит задачу на шаги `VNA-001`, `PS-002` с файлами и критерием готовности | нет (пишет план) | не обходит контракты, спорное выносит в «Требует уточнения» |
| `worker` | реализует конкретную задачу в 1–3 файлах | да | прибор — только через S2VNA, решётка — только через PS, GUI — через оркестратор |
| `hw-contracts` | контракты SCPI и PS + `src/vna`, `src/ps`, `src/dut` + их тесты | да | **сначала** `docs/contracts/*.md`, потом код и тесты; без имитатора PS и прямого RS-485 |
| `test-runner` | собирает и гоняет `ctest`, разбирает падения | только мелкая починка | **не ослабляет тесты** — ни `SKIP`, ни снятых проверок |
| `test-writer` | пишет новые тесты Catch2 | да (тесты) | тест обязан падать на сломанном коде |
| `debugger` | ищет первопричину | да | не глушит симптом, убирает отладочную печать |
| `reviewer` | ревью дифа перед коммитом | нет (`readonly`) | замечание = место + способ починки |
| `senior-reviewer` | архитектура, границы слоёв, долг | нет (`readonly`) | шаги, оставляющие проект рабочим; без паттернов ради паттернов |
| `security-auditor` | ответы S2VNA, сообщения PS, файлы серии, секреты стенда | нет (`readonly`) | каждая находка подтверждена строкой кода |
| `refactorer` | структура кода без смены поведения | да | **требует зелёных тестов до старта** |
| `documenter` | README, контракты `docs/contracts/`, отчёты | да (документы) | неверная документация чинится первой |

`readonly: true` у трёх ревьюеров — не пожелание, а настройка Cursor: такой
субагент физически не может править файлы.

## Рабочие процессы

Вызов: `/имя` в чате. Работают последовательно в этом же чате — каждый шаг
виден, можно вмешаться.

| Команда | Когда | Что делает |
|---|---|---|
| `/implement` | задача на 1–3 файла | `worker` → `test-runner` → `reviewer` |
| `/orchestrate` | фича на несколько модулей, SCPI или протокол PS | план → по каждой задаче `worker`→`test-runner`→[`debugger`]→`reviewer` → аудит → отчёт |
| `/refactor` | код работает, но неудобен | `senior-reviewer` → согласование → `refactorer` → `test-runner` |
| `/review-changes` | перед коммитом | `reviewer` + `security-auditor` по условию |
| `/audit` | перед выпуском, после перерыва | три ревьюера параллельно → факты от `test-runner` → сводный отчёт с оценкой |

Модули знаний, которые процессы и субагенты подтягивают по ходу:

| Скилл | Зачем |
|---|---|
| `build-and-test` | команды сборки Qt 6 (MinGW/UCRT64, Linux, macOS) и разбор типовых ошибок |
| `git-helper` | формат коммитов и безопасные операции git |
| `task-management` | файл состояния в `.cursor/workspace/` |
| `docs` | порядок обновления контракта, README, отчётов |
| `architecture-principles` | слои, владение, живучесть — для `/audit` и `/refactor` |
| `code-quality-standards` | чеклист ревью — для `/review-changes` и `/implement` |
| `security-guidelines` | чеклист аудита сети, прав и секретов |

## Правила

| Правило | Когда действует |
|---|---|
| `project-context.mdc` | **всегда** — стек, раскладка, команды, жёсткие ограничения стенда (S2VNA, PS, демо-данные) |
| `cpp-qt-style.mdc` | при работе с `src/**`, `include/**` |
| `testing.mdc` | при работе с `tests/**` |
| `commit-messages.mdc` | когда агент решит, что речь о коммитах и git |
| `git-workflow.mdc` | границы git: что можно без спроса, что только по просьбе |
| `security.mdc` | при работе с `src/vna`, `src/ps`, `src/dut`, `src/data`, `src/report`, `include/afar` |
| `documentation.mdc` | когда речь о документации |

## Хук

`hooks.json` перехватывает запуск команд оболочки и требует подтверждения
перед необратимыми: `git reset --hard`, `git push --force`, `git rebase`,
`git clean -f`, рекурсивное удаление каталогов. Не запрещает — спрашивает.

Правила лежат в `hooks/guard-shell.json`, добавлять свои можно туда, скрипт
трогать не нужно.

Отключить: удалить `hooks.json`. Проверить, что загрузился: Cursor Settings →
Hooks.

Скриптов два: `hooks/guard-shell.ps1` для Windows и `hooks/guard-shell.py`
для macOS/Linux. Оба записаны в `hooks.json`; там, где интерпретатора нет,
хук молча пропускается (`failClosed: false`), так что спрашивает тот, что
запустился. Правила у них общие — `guard-shell.json`.

Про `hooks/guard-shell.ps1` важно знать одно: его исходник намеренно
**только ASCII**. Windows PowerShell 5.1 читает `.ps1` без BOM как ANSI и
ломается на кириллице в коде, поэтому все русские формулировки вынесены в
UTF-8 файл `guard-shell.json`.

## Перенос в учётную запись

Проектная конфигурация действует только в этом репозитории. Чтобы работала
во всех проектах:

```powershell
.\.cursor\tools\install-global.ps1 -Mode Status   # что уже установлено
.\.cursor\tools\install-global.ps1 -Mode Copy     # независимая копия
.\.cursor\tools\install-global.ps1 -Mode Link     # соединения каталогов
.\.cursor\tools\install-global.ps1 -Mode Plugin   # плагин в dist\
.\.cursor\tools\install-global.ps1 -Mode Uninstall
```

`Copy` — обычная копия в `%USERPROFILE%\.cursor`, потом живёт своей жизнью.
`Link` — соединения каталогов: правишь в репозитории, меняется и глобально.
Требует, чтобы репозиторий оставался на месте.

По умолчанию переносится только переносимая часть. В проекте остаются
`rules/project-context.mdc`, `rules/cpp-qt-style.mdc`, `rules/testing.mdc`
и `skills/build-and-test`: глобально они давали бы неверные команды сборки
и чужие контракты стенда. Ключ `-IncludeProjectSpecific` переносит и их.

Субагенты при этом остаются осведомлёнными об этом проекте — у `test-runner`
команды `ctest`, у `debugger` разбор ошибок MinGW, у `senior-reviewer` схема
слоёв программы калибровки. Если в учётной записи уже стоит сборка из RMO,
одноимённые субагенты затрут друг друга — держите сборки проектными. Если переносите их в другой стек, эти разделы нужно переписать.

### Несколько машин

Файлы в `%USERPROFILE%\.cursor` Cursor между устройствами **не
синхронизирует**. Синхронизируется по учётной записи только то, что введено
в Cursor Settings → Rules как User Rules, и правила уровня команды из
панели управления на планах Team и Enterprise.

Рабочие варианты для нескольких машин:

1. **Плагин.** `-Mode Plugin` собирает каталог с манифестом
   `.cursor-plugin/plugin.json`. Положите его в git-репозиторий и подключите
   в Customize как источник плагинов — на каждой новой машине это одна
   установка. Для локальной проверки скопируйте каталог в
   `%USERPROFILE%\.cursor\plugins\local\` (именно скопируйте: соединения
   каталогов там не загружаются).
2. **Git-репозиторий конфигурации.** Держите `agents/`, `skills/`, `rules/`
   в отдельном репозитории и на каждой машине подключайте соединениями
   каталогов в `%USERPROFILE%\.cursor`. Обновление — `git pull`.
3. **Короткие предпочтения** (стиль ответов, язык) — в Cursor Settings →
   Rules. Они синхронизируются сами при входе в учётную запись.

Не складывайте ничего в `%USERPROFILE%\.cursor\skills-cursor\`: этот каталог
Cursor обслуживает сам.

## Если что-то не работает

- Субагента нет в списке по `/` — проверьте расширение `.md`, наличие
  `name` и `description` во frontmatter и перезапустите Cursor.
- Скилл не вызывается по `/` — папка должна содержать именно `SKILL.md`.
- Правило не применяется — сверьте `globs` с реальными путями и посмотрите
  статус в Customize → Rules.
- Хук не срабатывает — Cursor Settings → Hooks, затем канал вывода Hooks.
