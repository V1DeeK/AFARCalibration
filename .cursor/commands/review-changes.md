# /review-changes — проверка перед коммитом

По умолчанию смотрим подготовленные изменения: `git diff --staged`. Если
индекс пуст — берём `git diff`. Пользователь может назвать конкретные файлы
или каталог, тогда смотрим только их.

## Шаги

```
- [ ] 1. Собрать диф и определить область
- [ ] 2. Ревью — субагент reviewer
- [ ] 3. Аудит безопасности — субагент security-auditor (по условию)
- [ ] 4. Исправления — только с подтверждения пользователя
- [ ] 5. Повторная проверка
```

**Шаг 1.** Выведи список изменённых файлов и коротко скажи, что это за правка.

**Шаг 2.** `reviewer` разбирает изменения и выдаёт замечания по приоритету.
Перед запуском прочитай скилл `code-quality-standards` и передай его
требования в задании субагенту: субагент этот чат не видит.

**Шаг 3.** Запускай `security-auditor` параллельно с ревью, если диф трогает
`protocol/`, `connection/`, `streams/`, `auth/` или `record/`. Эти модули
работают с недоверенными данными и учётками — здесь цена ошибки другая.
В задание субагенту включи чеклист из `security-guidelines`.

**Шаг 4.** Покажи сводку и спроси, что чинить. Сам ничего не правь без ответа:
пользователь мог сознательно оставить что-то на потом. Согласованные правки
выполняет `worker`.

**Шаг 5.** После правок — `test-runner` и повторное ревью только изменённого.

## Итог

```
Файлов в дифе: N
Критично: N   Стоит исправить: N   Мелочи: N
Безопасность: проверено / не требовалось
Тесты: N пройдено, M упало
Вывод: готово к коммиту | требует правок
```

Сообщение коммита при необходимости собирай по скиллу `git-helper`. Сам
`git commit` и `git push` не выполняй без явной просьбы.
