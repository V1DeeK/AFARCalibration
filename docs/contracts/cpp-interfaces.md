# Контракт C++-интерфейсов и автомата состояний

Источник: AFAR-RX-CAL-SW-TZ-01, ред. 1.0 от 29.08.2026, т. 8.3 (типы и интерфейсы), т. 8.4 (автомат), т. 8.2 и т. 8.5 (слои и параллельность), т. 1.3 (границы v1.0 и расширения).

Этот документ — канонический контракт для заголовков `include/afar/` (задачи VNA-001, DUT-001, CORE-002). Имена полей и методов совпадают с т. 8.3 посимвольно. Упрощать сигнатуры, сливать типы с ТЗ этапа фазирования или добавлять методы «на будущее» нельзя.

Код в документ не копируется: ниже — имена, типы, диапазоны и обязательства. Реализация не входит в DOC-003.

---

## 1. Слои и параллельность

Модули т. 8.2, имеющие отношение к этому контракту:

| Модуль | Ответственность |
|--------|-----------------|
| `app-ui` | окна, графики, мастер запуска, матрица кодов |
| `measurement-core` | автомат состояний, очередь операций, пауза и восстановление |
| `vna-scpi` | SCPI-транспорт и драйвер C2220/S2VNA |
| `dut-controller` | сменные драйверы контроллера АФАР |
| `data-store` | транзакционная запись HDF5, журнал попыток, контрольные суммы |
| `simulator` | программные имитаторы C2220 и контроллера |

Правила слоёв (т. 8.2):

- GUI (`app-ui`) **не** посылает аппаратные команды напрямую.
- Все команды оборудованию проходят через `measurement-core`.
- `measurement-core` сериализует изменение состояния стенда.

Правила параллельности (т. 8.5):

- Аппаратная последовательность выполняется **строго последовательно** в **одном** рабочем контексте `measurement-core`.
- Запись данных может идти отдельным потоком через **ограниченную очередь**.
- Следующее состояние изделия **не задаётся**, пока предыдущие данные не приняты в очередь и не подтверждено отсутствие критической ошибки.
- При заполнении очереди измерение приостанавливается; данные **не отбрасываются**.

Драйверы (`IVna`, `IDutController`) не содержат бизнес-логики серии. Оркестратор владеет тайм-аутами, отменой, паузой и безопасным остановом.

## 2. `SweepConfig`

Конфигурация свипа VNA. Поля т. 8.3 полностью:

| Поле | Тип | Смысл |
|------|-----|--------|
| `f_start_hz` | `std::uint64_t` | начальная частота, Гц |
| `f_stop_hz` | `std::uint64_t` | конечная частота, Гц |
| `points` | `std::uint32_t` | число точек свипа |
| `power_dbm` | `double` | мощность порта, дБм |
| `ifbw_hz` | `std::uint32_t` | полоса ПЧ, Гц |
| `averages` | `std::uint16_t` | число усреднений |

Это не `SweepConfig` ТЗ этапа фазирования (там ось задаётся вектором `frequency_hz` без `f_start_hz` / `f_stop_hz` / `points`). Смешивать типы нельзя.

Допустимые пределы прибора и профиля серии проверяет конфигурация **до** вызова `IVna::configure` (FR-02, HW-VNA-02). Сам интерфейс полей не сужает.

## 3. `ComplexSweep`

Результат одного измерения S21. Поля т. 8.3 полностью:

| Поле | Тип | Смысл |
|------|-----|--------|
| `frequency_hz` | `std::vector<std::uint64_t>` | ось частот, Гц; длина равна `points` после успешного свипа |
| `s21` | `std::vector<std::complex<double>>` | комплексные отсчёты S21 той же длины |
| `overload` | `bool` | признак перегрузки приёмника |

После `measure_s21` оркестратор проверяет совпадение длин, конечность чисел и `overload` (FR-07). Интерфейс не молча обрезает и не интерполирует ось.

## 4. `IVna`

Чисто виртуальный интерфейс векторного анализатора. Методы т. 8.3 полностью, без добавлений:

| Метод | Сигнатура | Обязательство |
|-------|-----------|---------------|
| деструктор | `virtual ~IVna() = default` | не выполняет блокирующих аппаратных операций |
| `connect` | `void connect()` | установить связь с прибором |
| `identify` | `std::string identify()` | идентификация прибора (ответ в духе `*IDN?`); серия не стартует, если модель не разрешена профилем (HW-VNA-01) |
| `configure` | `void configure(const SweepConfig&)` | применить диапазон, точки, ПЧ, мощность, усреднение, параметр S21 |
| `measure_s21` | `ComplexSweep measure_s21()` | одиночный свип и чтение комплексного S21 вместе с осью частот |
| `drain_errors` | `std::vector<std::string> drain_errors()` | выбрать очередь ошибок прибора после группы команд (HW-VNA-03) |
| `abort` | `void abort() noexcept` | прервать текущую операцию прибора; **только этот метод `IVna` помечен `noexcept`** |

Прямой доступ к приёмникам (`SYSTem:RECeiver:DIRect:ACCess`) в интерфейс **не входит**. Программа его сама не включает (HW-VNA-05); проверка состояния — обязанность драйвера/оркестратора, не новый метод `IVna`.

Транспорт (Socket / COM), перечень SCPI и тайм-ауты — в `docs/contracts/vna-c2220-scpi.md`, не в этом интерфейсе.

## 5. `DutState`

Электронное состояние одного канала изделия. Поля и диапазоны т. 8.3:

| Поле | Тип | Диапазон | Комментарий ТЗ |
|------|-----|----------|----------------|
| `channel` | `std::uint8_t` | 1…16 | номер канала |
| `att_code` | `std::uint16_t` | 0…63 | «0..63 in this project»; тип **не** сужается до `uint8_t` |
| `phase_code` | `std::uint8_t` | 0…63 | код фазовращателя |

Значения вне диапазона оркестратор отклоняет **до** `apply`. Это состояние этапа 1 (один активный канал). Вектор кодов на 16 каналов (`ChannelCode`, `IAfarController`) относится к этапу фазирования и сюда не переносится.

## 6. `IDutController`

Чисто виртуальный интерфейс контроллера АФАР этапа 1. Методы т. 8.3 полностью:

| Метод | Сигнатура | Обязательство |
|-------|-----------|---------------|
| деструктор | `virtual ~IDutController() = default` | не выполняет блокирующих аппаратных операций |
| `connect` | `void connect()` | установить связь с контроллером |
| `apply` | `void apply(const DutState&)` | задать канал, код аттенюатора и код фазы |
| `readback` | `DutState readback()` | прочитать обратно применённое состояние, если контроллер это поддерживает |
| `temperature_c` | `double temperature_c()` | температура, °C |
| `set_safe_state` | `void set_safe_state() noexcept` | безопасное состояние всех каналов; **только этот метод `IDutController` помечен `noexcept`** |

Состояние считается применённым только после положительного подтверждения либо после выдержки профиля, если обратного чтения нет (HW-DUT-03). Способ подтверждения фиксируется в метаданных серии, не новым методом интерфейса.

При потере связи оркестратор прекращает новые свипы, пытается вызвать `set_safe_state` и переводит автомат в `ERROR` (HW-DUT-04).

### 6.1. Чего нет в т. 8.3 — не добавлять

HW-DUT-02 перечисляет среди команд драйвера аппаратный сброс и проверку связи. В минимальном C++-интерфейсе т. 8.3 методов `reset` и `identify` у `IDutController` **нет**.

В этот контракт и в заголовок `IDutController` их **не включать**, пока нет отдельного уточнения (открытый вопрос плана, п. 14). Не подменять их вызовами из GUI и не выдумывать кадры протокола изделия.

Базовые транспорты (последовательный порт и TCP/IP) задаёт HW-DUT-01; конкретные кадры, CRC, скорость и порядок байтов — отдельная спецификация, не часть этого интерфейса.

## 7. Ошибки и время жизни объектов

Из завершающих абзацев т. 8.3:

- Исключения драйверов преобразуются в типизированные ошибки уровня приложения.
- В деструкторах **не допускаются** блокирующие аппаратные операции.
- Безопасный останов выполняется **явным** методом оркестратора (через `set_safe_state` / `abort`), а не из деструктора драйвера.

`abort` и `set_safe_state` — `noexcept`: реализация не бросает исключения наружу. Сбой безопасного останова фиксируется в журнале, но не разворачивает стек через деструктор.

## 8. Автомат состояний (т. 8.4)

Имена состояний:

`IDLE`, `CONNECTING`, `SELF_TEST`, `READY`, `RUNNING`, `PAUSING`, `PAUSED`, `STOPPING`, `ABORTED`, `FINALIZING`, `COMPLETE`, `ERROR`, `RECOVERY`.

Допустимые цепочки т. 8.4 — без добавленных переходов:

```
IDLE → CONNECTING → SELF_TEST → READY → RUNNING
RUNNING → PAUSING → PAUSED → RUNNING
RUNNING → STOPPING → ABORTED
RUNNING → FINALIZING → COMPLETE
любое активное состояние → ERROR → RECOVERY или ABORTED
```

Таблица разрешённых рёбер:

| Из | В | Смысл |
|----|---|--------|
| `IDLE` | `CONNECTING` | начало подключения стенда |
| `CONNECTING` | `SELF_TEST` | связь установлена, самопроверка |
| `SELF_TEST` | `READY` | стенд готов к серии |
| `READY` | `RUNNING` | старт перебора |
| `RUNNING` | `PAUSING` | команда «Пауза» (FR-10): дождаться конца текущего свипа |
| `PAUSING` | `PAUSED` | данные сохранены, изделие в `safe_state` |
| `PAUSED` | `RUNNING` | «Продолжить»: повторная проверка связей, первое незавершённое состояние |
| `RUNNING` | `STOPPING` | подтверждённый останов (FR-11) |
| `STOPPING` | `ABORTED` | серия закрыта как прерванная; данные пригодны для анализа |
| `RUNNING` | `FINALIZING` | штатное завершение перебора |
| `FINALIZING` | `COMPLETE` | серия закрыта успешно |
| любое активное | `ERROR` | отказ оборудования, потеря связи, критическая ошибка очереди |
| `ERROR` | `RECOVERY` | путь восстановления |
| `ERROR` | `ABORTED` | отказ от восстановления, серия закрыта |

Активные состояния для ребра в `ERROR`: все перечисленные, кроме конечных `IDLE`, `COMPLETE` и `ABORTED`. Из `ERROR` дальше только `RECOVERY` или `ABORTED`. Исходящие рёбра из `RECOVERY` т. 8.4 не задаёт — добавлять `RECOVERY → RUNNING` и подобные в автомат нельзя, пока это не уточнено отдельным решением. Обнаружение незакрытой серии при следующем запуске (FR-12) — сценарий оркестратора, а не неявное новое ребро.

### 8.1. Недопустимый переход

Любой переход, которого нет в таблице выше, **отклоняется (reject)**. При reject:

- автомат остаётся в текущем состоянии;
- **ни одной** команды оборудованию не отправляется (`IVna` и `IDutController` не вызываются);
- в журнал пишется факт отклонения.

Проверка допустимости — до любого I/O.

### 8.2. Журнал переходов

Каждый **разрешённый** переход регистрируется с:

- временем UTC;
- причиной;
- пользователем;
- снимком актуального состояния стенда.

Формат записи — JSONL серии (`run-events.jsonl`, т. 9); этот контракт фиксирует состав полей перехода, не схему файла.

## 9. Точки расширения этапа 2/3

В приёмку v1.0 **не входят** (т. 1.3): механическое управление сканером, кодирование Хадамарда, измерение диаграмм лучей, расчёт моноимпульсной характеристики. Для них резервируются **только имена**. Реализации, методов и заголовков в этапе 1 нет.

Зарезервированные имена программных интерфейсов (не реализовывать в v1.0):

| Имя | Назначение |
|-----|------------|
| `IScanner2D` | управление сканером ближнего поля |
| `Position3d` | координаты зонда |
| `ScannerStatus` | статус сканера (homed, in_position, e_stop, limit, door_open) |
| `IHadamard` | кодирование / декодирование Хадамарда |
| `IFarFieldPattern` | диаграммы лучей (ДН), в том числе NF–FF |
| `IMonopulse` | моноимпульсная характеристика |
| `IAfarController` | контроллер решётки этапа фазирования (вектор кодов на 16 каналов); **не** синоним `IDutController` |

Зарезервированные имена модулей / схем (без файлов и JSON Schema в этапе 1):

| Имя | Назначение |
|-----|------------|
| `scanner-driver` | драйвер сканера |
| `hadamard` | состояния и фактическая матрица Хадамарда |
| `nfff` | преобразование ближнее–дальнее поле |
| `beam-analysis` | HPBW, лепестки, моноимпульс |
| `afar.stage2.*` | схемы данных этапа 2 |
| `afar.stage3.*` | схемы данных этапа 3 |

Имена нельзя занимать под сущности этапа 1. Методы и поля этих типов в данный контракт не входят.
