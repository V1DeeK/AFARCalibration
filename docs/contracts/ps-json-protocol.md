# Контракт обмена с PS изделия (JSON, TCP + UDP)

Источники (папка `documentation/` рабочей копии пользователя, в git не входит):

- `structural_scheme_v2.docx` — «Протокол взаимодействия»: транспорт, обёртка
  сообщений, режимы, сервисные команды;
- `Описание протокола Json to RS-485.docx` — справочно: чем PS управляет по
  RS-485. Программа этими модулями не управляет и их JSON не шлёт;
- тот же протокол со стороны АРМ — `protocol/documentation/rmo_ps_protocol.md`
  в репозитории `V1DeeK/RMO` (версия 1.0, 2026-10-09). Расхождений с ним в
  общей части быть не должно.

Статус: черновик, 2026-10-12. Версия протокола — `"1.0"`.

Программа калибровки — **только клиент**. Она шлёт PS команды сервисного
режима из «Протокола взаимодействия» (v2) по JSON и показывает, что ушло и что
пришло по TCP и UDP. Все действия с железом (решётка, АЦП, модули RS-485)
выполняет PS. Своих команд сверх v2 программа не вводит; RS-485 — только
`rs485_send` из v2. Имитатора PS в программе нет: PS делает коллега.

Пометки:

- **[предложение]** — в исходных документах этого нет; принято, чтобы клиент
  можно было написать. Требует согласования с разработчиком PS.
- Открытые вопросы — раздел 8.

---

## 1. Каналы

| Канал | Транспорт | Порт PS | Направление | Формат |
|---|---|---|---|---|
| Управление | TCP | 49600 | двусторонний | NDJSON |
| Телеметрия | UDP | 49601 по умолчанию, фактически — `tlm_port` из `hello` | PS → программа | JSON, одна датаграмма — одно сообщение |

Программа — TCP-клиент. Адрес PS — параметр профиля стенда, в git не
хранится.

## 2. Обёртка сообщения

UTF-8, одна строка JSON, завершённая `\n`. Переводы строк внутри запрещены.
Строка длиннее 1 МиБ — разрыв соединения **[предложение]**.

| Поле | Значение |
|---|---|
| `msg_type` | имя команды или события |
| `msg_class` | `"command"`, `"response"`, `"event"` |
| `msg_count` | 0–255, счётчик по модулю 256 |
| `payload` | объект JSON, пустой — `{}` |

- Команда: программа → PS, `msg_count` — свой счётчик команд.
- Ответ: PS копирует `msg_type` и `msg_count` команды; в `payload` —
  `status` и фактически установленные значения параметров.
- Событие: PS → программа без запроса, свой счётчик PS.

Статусы: `"OK"`, `"BUSY"`, `"NOT_SUPPORTED"`, `"INVALID_ARGUMENT"`,
`"HW_NOT_READY"`. При статусе не `"OK"` параметры изделия не меняются.

Тайм-ауты клиента **[предложение, как в РМО]**: ответ на команду — 2 с;
`keep_alive` при отсутствии обмена 5 с; связь потеряна, если нет ответа на
`keep_alive` или нет сообщений от PS дольше «простой + 3 с». После потери —
переподключение с новым `hello`, неотвеченные команды не досылаются.

## 3. Управление изделием

| `msg_type` | Payload команды | Payload ответа (кроме `status`) |
|---|---|---|
| `hello` | `ver`, `tlm_ip`, `tlm_port` | `ver` PS (+ эхо). Несовместимая версия — `"NOT_SUPPORTED"` |
| `keep_alive` | `{}` | — |
| `set_mode` | `mode` | `mode` |
| `get_state` | `{}` | `mode`, `state` |

`hello` — первая команда после соединения, до неё всё отклоняется с
`"NOT_SUPPORTED"`. Версии совместимы при одинаковой старшей цифре.

Режимы `mode`: `"IDLE"`, `"FULL_SCAN_FREQ"`, `"OPERATIONAL"`, `"SERVICE"`.
Программе калибровки нужны только `IDLE` и `SERVICE`; вход в `SERVICE` —
только из `IDLE` в состоянии `READY`. В `FAULT` `set_mode` отвечает
`"HW_NOT_READY"`.

Состояния `state` в `IDLE`: `INIT`, `SELF_TEST`, `READY`, `FAULT`. Состояния
вложенного КА `SERVICE` не определены (вопрос 8.3).

## 4. Сервисный режим

Команды раздела принимаются только в `SERVICE`, в остальных режимах —
`"NOT_SUPPORTED"`. При выходе из `SERVICE` PS сам восстанавливает рабочую
конфигурацию.

### 4.1. `set_phase_atten` / `get_phase_atten` — коды решётки

`payload.ch` — ровно 16 элементов `{"n": 1…16, "ph": 0…63, "att": 0…63}`,
номера без повторов. Иначе `"INVALID_ARGUMENT"`, решётка не меняется. В ответе
обеих команд — коды, **считанные из микросхем** после записи. Это обратное
чтение для HW-DUT-03.

```json
{"msg_type":"set_phase_atten","msg_class":"command","msg_count":70,"payload":{"ch":[{"n":1,"ph":0,"att":0},{"n":2,"ph":16,"att":4}]}}
```

(в примере два элемента; передаются все 16)

### 4.2. `set_adc` / `get_adc` — приёмный тракт

| Поле | Тип | Смысл |
|---|---|---|
| `lo` | целое, Гц | частота гетеродина приёмника, > 0 и ≤ 100 ГГц (диапазон проверяет PS) |
| `bw` | целое, Гц | полоса RF |
| `fs` | целое, Гц | частота дискретизации |
| `gain` | число, дБ | усиление, только ручное |

В ответе — фактически установленные значения (`lo` может сдвинуться на шаг
сетки синтезатора).

### 4.3. `set_beam_azimuth`, `set_beam`, `get_beam`

`set_beam_azimuth`: `az`, град, −30…+30. `set_beam`: `beam`, целое ≥ 0.
`get_beam` отвечает `src` (`"azimuth"`, `"table"`, `"codes"`, `"none"`) и `az`
или `beam`.

### 4.4. `rs485_send` — сырые байты в линию

`payload.data` — HEX-строка чётной длины (`"01A3FF"`). Ответ подтверждает
передачу в линию; ответ устройства не возвращается (вопрос 8.1).

## 5. Телеметрия (UDP) **[предложение, как в РМО §9]**

Одна датаграмма — одно сообщение в той же обёртке: `msg_type` =
`"telemetry"`, `msg_class` = `"event"`, свой счётчик PS. Период 1 с. Начинается
после `hello`. По пропускам `msg_count` клиент считает потери; битые
датаграммы отбрасывает и считает.

| Поле `payload` | Тип | Смысл |
|---|---|---|
| `time` | целое, мс | время изделия, UTC |
| `uptime` | целое, с | время с включения |
| `mode`, `state` | строки | режим и состояние |
| `devices` | объект | итоги самопроверки: `"OK"`, `"FAIL"`, `"NOT_CHECKED"` |
| `temperature` | объект | температуры узлов, °C |
| `power` | объект | напряжения шин, В |

## 6. Реакция на команды в режимах

| Команда | IDLE | SERVICE | Прочие режимы |
|---|---|---|---|
| `hello`, `keep_alive`, `get_state` | да | да | да |
| `set_mode` | в `READY`; в `FAULT` — `"HW_NOT_READY"` | да | по `rmo_ps_protocol.md` §8 |
| команды раздела 4 | `"NOT_SUPPORTED"` | да | `"NOT_SUPPORTED"` |

## 7. Связь с ТЗ этапа 1

| ТЗ | Как закрывается через PS |
|---|---|
| HW-DUT-02 «задать коды», «прочитать обратно» | `set_phase_atten` / `get_phase_atten` |
| HW-DUT-02 «температура и флаги» | телеметрия: `temperature`, `devices` |
| HW-DUT-02 «безопасное состояние» | все 16 каналов: аттенюатор 63, фаза 0 |
| HW-DUT-03 подтверждение | коды в ответе `set_phase_atten` совпали с заданными во всех 16 каналах |
| HW-DUT-04 потеря связи | разрыв TCP или тайм-аут ответа |

Реализация — `src/dut/PsDutController`. При измерении одного канала остальные
15 получают аттенюатор 63 и фазу 0; те же коды на всех 16 — безопасное
состояние. Решение пользователя 2026-10-12 (т. 14 пп. 2, 5 ТЗ); значения —
параметры драйвера, не константы протокола.

Всё, что относится к сервисному режиму и сервисным командам, ведёт эта
программа, а не АРМ RMO (решение пользователя 2026-10-12). Вкладка
«Параметры PS»: ручные команды раздела 4, «Пакет» — любая команда с payload,
набранным вручную (без проверки на клиенте), «Приёмка» — автопрогон
`src/ps/PsServiceCheck` по разделам 3–6 с отчётом Markdown: команды и ответы
по TCP и телеметрия по UDP (режим в датаграммах меняется вслед за `set_mode`).
Приёмка заканчивается безопасным состоянием 63/0 и возвратом в `IDLE`.

Связь вкладки с PS не зависит от подключения анализатора: анализатор PS не
трогает.

## 8. Открытые вопросы к разработчику PS

1. Ответ устройства RS-485 на `rs485_send`.
2. Безопасное состояние решётки: принято 63/0 на всех неактивных каналах
   (раздел 7) — подтвердить, что это безопасно для тракта.
3. Состояния вложенного КА `SERVICE`.
4. Спектр в `SERVICE`: команды или события, которыми PS отдаёт спектр с АЦП,
   нет; `send_sff_result` идёт только в `FULL_SCAN_FREQ`.
5. Состав телеметрии: какие температуры и шины передаются, есть ли
   температура платы решётки для `temperature_c()`.
